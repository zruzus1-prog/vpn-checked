## Как отсекаются отваливающиеся и медленные узлы

1. Быстрый отсев: два HTTPS-запроса через прокси к Google gstatic и Cloudflare. Нужны проверенный TLS, код 204, пустое тело и каждый ответ не дольше 4 секунд
2. Все выбранные поддерживаемые конфигурации, прошедшие быстрый отсев, допускаются к углублённой проверке: лимиты выбора и углублённых проверок одинаковы, по 512. При превышении лимита или нехватке времени отчёт явно показывает неполное покрытие
3. Две отдельные загрузки по **2 МиБ**, до и после окна наблюдения. Каждая должна загрузиться целиком со средней скоростью не ниже **256 КиБ/с, примерно 2 Мбит/с**. Учитывается время установления соединения; частичные загрузки не засчитываются
4. Повторные HTTPS-проверки примерно на 15-й, 30-й и 45-й секундах через тот же процесс core и тот же прокси. Любой сбой отклоняет узел. Проверяется доступность в течение этого окна, а не сохранность одного долгого TCP-соединения
5. YouTube и ChatGPT запрашиваются по HTTPS без cookies, логинов, токенов и перехода по редиректам. Требуются HTTP 200 и узнаваемое содержимое настоящей страницы. 403, 429, редиректы, известные страницы CAPTCHA/проверки браузера/согласия, блокировки и неопознанные страницы не засчитываются

В начале короткой метки узла сохранено безопасно очищенное имя и флаг из исходного списка, затем протокол и короткий идентификатор. Страна/флаг — заявление источника, не проверенная геолокация сервера; если имени нет, указано «Страна не указана». Задержка GitHub не включается в имя: Karing отдельно показывает задержку из вашей сети. Технические статусы, время UTC, задержка GitHub и скорость находятся в отчёте. Отчёт содержит оба замера скорости, длительность окна, результаты каждой проверки сервиса, источники, счётчики и причины отсева. HTML страниц не сохраняется в отчёте.

**Это не проверка воспроизведения видео, входа в аккаунт или ответа на запрос к ChatGPT.** Главная страница может открываться, когда видеопотоки, аккаунт или чат не работают. Порог 2 Мбит/с отсеивает очень медленные узлы, но не обещает HD/4K. Проверка заголовков, текста HTML и элементов форм отличает настоящую проверочную страницу от одного лишь слова CAPTCHA внутри скриптов/настроек сайта. В отчёте сохраняются только именованные признаки и счётчики, без HTML, cookies и токенов.

HTTP 403 автоматического запроса означает, что этот тест доступ не подтвердил; это само по себе не доказывает, что сайт не откроется в обычном браузере через тот же сервер. Отчёт не называет все отклонённые узлы неисправными. Эвристики содержимого намеренно консервативны: изменение сайта или защитная проверка могут исключить рабочий узел. Критерии не ослабляются автоматически.

## Откуда выполняется проверка

С GitHub-hosted runner, **не из России и не из вашей сети**. Узел может пройти тест на GitHub и быть заблокирован у российского мобильного или домашнего провайдера. При переключении Wi-Fi/мобильной сети результат может отличаться. Стабильность на протяжении 45 секунд не гарантирует часы работы; узел может перестать работать сразу после проверки. Проект не обещает «лучшие серверы во всём интернете».

Публичные прокси недоверенные: видят IP и метаданные, могут вести журналы. Пользуйтесь HTTPS, не отключайте проверку сертификатов и не передавайте чувствительные данные через неизвестные узлы.

## Источники и границы нагрузки

Публичные списки igareck/vpn-configs-for-russia и Diversan313/apex-parser, точные пути указаны в [NOTICE.md](NOTICE.md) и checker.py. Каждый источник ограничен 4 МиБ и 20 000 строками конфигураций. Превышение ограничения делает источник недоступным для этого запуска; строки не обрезаются молча. Дедупликация выполняется по эффективным разобранным параметрам, а не по меткам. Порядок определяется SHA-256 нормализованной конфигурации, без случайной выборки. Каждый запуск пытается оценить все уникальные поддерживаемые конфигурации, максимум 512; отдельного меньшего лимита углублённых проверок нет. Одновременно работают 4 проверки на обычном `ubuntu-24.04` runner.

Бюджет всего checker — 90 минут, GitHub job — 95 минут. DNS ограничен 5 секундами; у каждого HTTPS-запроса есть тайм-аут и ограничение размера. Кандидаты без достаточного остатка времени получают причину `budget`, а не ложный результат сетевого сбоя. Максимум полезной нагрузки на углублённый тест: 4 МиБ для скорости + до 4 МиБ страниц; до 4 ГиБ на 512 кандидатов, плюс небольшой быстрый отсев, исходные списки, загрузка core и протокольные накладные расходы. Реальный объём меньше при ранних отказах. Если бы все 512 дошли до полного 45-секундного окна, только окна при четырёх потоках заняли бы 96 минут; поэтому максимальная ёмкость не означает гарантии полного покрытия за один запуск.

В отчёте схемы 3 `coverage.complete_supported` истинно только когда доступны все три источника и каждому поддерживаемому уникальному кандидату дана завершённая оценка, без пропусков по лимиту выбора, лимиту углублённых проверок или времени. Счётчики `candidate_cap_skipped`, `deep_cap_skipped`, `deadline_skipped` показывают ограничения явно. Завершённая оценка может закончиться отказом DNS, запуска core, быстрого теста, скорости или стабильности; это не означает, что каждый узел прошёл все стадии. Поле `sampled` сохранено для совместимости и теперь означает число выбранных конфигураций без случайной выборки.

По каждому источнику указаны исходные строки, поддерживаемые строки, уникальные конфигурации, дубликаты и фиксированные категории отклонений без исходных учётных данных. `unique_endpoints` считает сочетания протокола, адреса и порта; разные настройки одного адреса могут быть отдельными конфигурациями. Неподдерживаемые варианты не объявляются неисправными. Даже `complete_supported=true` не означает, что проверены все форматы исходных подписок или подтверждена работа в вашей сети.

## Форматы и защита

Поддерживается ограниченное подмножество: Shadowsocks AES-GCM/ChaCha20-Poly1305, в том числе встроенный `obfs-local` только с `obfs=tls` и одним `obfs-host`; Trojan TLS; VLESS TLS/Reality; VMess TLS с alterId=0; Hysteria2 TLS (включая salamander и `upmbps=0`); TCP/WebSocket. Для VLESS поддержаны синоним `raw` → TCP, только пустая TCP-маскировка `headerType=none`/`headertype=none` и `packetEncoding` со значениями `xudp`, `packetaddr` или явным пустым значением. Отсутствующий `packetEncoding` соответствует стандартному `xudp`; явное пустое значение сохраняется отдельно.

`obfs-local` реализован внутри закреплённого sing-box: отдельные плагины не скачиваются и команды из URI не запускаются. Разрешены ровно два параметра, `obfs=tls` и `obfs-host`; дубликаты, дополнительные опции, escape-последовательности, управляющие символы и слишком длинные значения отклоняются. `obfs-host` сохраняется как ограниченная строка маскировки, включая необычные знаки источника: это не адрес назначения и не домен для проверки сертификата. TLS-obfs — имитация TLS поверх шифрования Shadowsocks, а не настоящий дополнительный TLS-сеанс. Проверка сертификатов внутренних HTTPS-запросов не отключается. См. [официальное описание Shadowsocks](https://sing-box.sagernet.org/configuration/outbound/shadowsocks/) и [встроенную реализацию obfs-local v1.14.2](https://github.com/SagerNet/sing-box/blob/v1.14.2/transport/sip003/obfs.go).

gRPC, XHTTP, HTTP-заголовочная маскировка, остальные плагины, неизвестные параметры, небезопасный TLS и неподдержанные варианты пропускаются. Расширение совместимости не ослабляет критерии скорости, стабильности и сервисных проверок.

Серверные домены разрешаются один раз, все полученные адреса должны быть публичными; core получает фиксированный IP. Loopback, private, link-local, multicast и переходные IPv6-адреса блокируются. В экспортируемых URI сохраняется исходный hostname: Karing разрешает его заново; проверка runner не защищает клиент от последующей смены DNS. Произвольные команды из конфигураций не исполняются. Нет прямого fallback-трафика вместо прокси.

URI уже публичны; полученная подписка также публичная. Ваши логины, cookies, пароли и API-ключи не нужны. Логи содержат счётчики; отчёт — хеш-идентификаторы, показатели и результаты, без исходных учётных данных узлов.

## Свежесть и диагностика

Расписание: примерно каждые 6 часов, `23 */6 * * *` UTC. GitHub может задерживать расписание или отключить его в неактивном публичном репозитории. Полная недоступность источников, отсутствие поддерживаемых кандидатов или общий сбой запуска core останавливают публикацию. Если проверки прошли, но подходящих узлов нет, публикуется пустая подписка. Старые узлы не подмешиваются.

Если workflow не завершился, прежняя публикация остаётся доступной со **старой датой**. Считайте отчёт старше 12 часов устаревшим. Статический raw URL не может автоматически отозвать уже скачанные узлы. Ручной запуск: Actions → Check public subscription → Run workflow.

Для диагностики, а не как замена основной ссылки: `subscription-gpt.txt` содержит узлы со стабильностью/скоростью и подтверждённой страницей ChatGPT; `subscription-youtube.txt` — аналогично для YouTube. Они могут содержать узлы, отсутствующие в основном списке. Их счётчики находятся в report.json. Основная ссылка всегда требует оба сервиса.

## Запуск и устройство

Python 3.12+, системный curl, официальный sing-box с фиксированными версией и SHA-256. pip-зависимостей нет. Core скачивается только из официального релиза; SHA-256 проверяется до извлечения. GitHub Actions закреплены полными commit SHA. Задание проверки не имеет write-token; публикация выполняется отдельным заданием после проверки состава, свежести, хешей и согласованности всех трёх файлов.

Ветка `checked` содержит только последний результат и лицензионные уведомления; история этой генерируемой ветки заменяется при публикации. Исходная ветка `main` сохраняется.

Локальные тесты не обращаются к реальным прокси:

    python3 -m unittest discover -s tests -v

Реальный запуск соединяется с недоверенными публичными серверами:

    python3 fetch_core.py
    python3 checker.py
    python3 validate_output.py public
