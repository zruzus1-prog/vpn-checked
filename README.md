# Проверяемая подписка для Karing

## Ссылка, которой вы уже пользуетесь

https://raw.githubusercontent.com/zruzus1-prog/vpn-checked/checked/subscription-youtube.txt

Адрес не меняется. В этом списке нужны строгий TLS, успешные повторные проверки
доступности, два полных теста скорости и узнаваемая главная страница YouTube.
HTTP 403 от ChatGPT не исключает узел из этого списка.

**Это проверка страницы YouTube, не воспроизведения видео.** Видеопотоки Googlevideo,
приложение, QUIC, вход в аккаунт и реальный ответ ChatGPT не проверяются. Публичные
прокси недоверенные; проверка не устанавливает их владельцев или отсутствие логов.
Не отключайте проверку сертификатов и используйте HTTPS.

Другие списки:
- `subscription-gpt.txt`: та же базовая проверка плюс страница ChatGPT
- `subscription.txt`: базовая проверка и обе страницы
- [report.json](https://raw.githubusercontent.com/zruzus1-prog/vpn-checked/checked/report.json):
  время, условия, причины отказа и результаты по каждому узлу

Метка сохраняет безопасно очищенное исходное имя, протокол и стабильный ID.
Флаг/страна в исходном имени не являются проверенной геолокацией. Задержку из
своей сети показывает Karing. Все байты исходной ссылки до `#` сохраняются:
пароли, адрес, query, transport и исходный VMess payload не переписываются.

## Два списка YouTube: основной и резервный

- [Основной, до 40 узлов](https://raw.githubusercontent.com/zruzus1-prog/vpn-checked/checked/subscription-youtube-stable.txt)
- [Резерв, остальные прошедшие](https://raw.githubusercontent.com/zruzus1-prog/vpn-checked/checked/subscription-youtube-reserve.txt)

Оба списка содержат **только успешные проверки текущего запуска**. Они не
пересекаются, а вместе дают весь прежний `subscription-youtube.txt`, который
остаётся совместимым полным списком. В основной попадает не более 40 узлов;
если доказательств мало, их будет меньше или список будет пустым.

Для основного нужны одновременно:

1. Успешная полная текущая проверка TLS/HTTPS/скорости/стабильности/страницы YouTube
2. Не менее трёх успешных независимых запусков за последние 48 часов. Между
   учитываемыми успехами не менее 90 минут, общий интервал не менее 6 часов
3. Не менее 90% успехов среди **реально выполненных наблюдений**, а последние
   два наблюдения успешны. Это не оценка 90% времени безотказной работы
4. Оба образца скорости во всех успешных наблюдениях не ниже 512 КиБ/с

Обычный порог 256 КиБ/с остаётся достаточным для полного и резервного списков.
Сначала оцениваются доля успехов и число разнесённых по времени успехов, затем
худшая успешная скорость, медианная задержка, стабильный ID. После квалификации
берётся не более одного узла на проверенный IP endpoint. Это уменьшает число повторяющихся адресов в основном списке Karing, но не доказывает независимость операторов или стран.
Все отсеянные только по разнообразию/лимиту варианты остаются в резерве.
Оценки ChatGPT не влияют на эти критерии YouTube.

## История кандидатов и свежие перепроверки

Последний успешно проверенный узел остаётся кандидатом максимум 48 часов с его
последнего **реального присутствия в исходном источнике**. Успешная перепроверка,
публикация и отсутствие в новом источнике этот срок не продлевают. Отсутствие в
источнике само по себе не считается отказом. Каждый сохранённый кандидат заново
проходит весь текущий парсер, DNS/public-IP защиту, официальный core и сетевые
тесты; прошлый успех никогда не переносится в новый список автоматически.

При первом запуске история восстанавливается из последних совместимых публикаций
собственной ветки `checked`, не из утверждений внешних источников. Проверяются
GitHub commit, успешный exact Actions run/attempt, успешный publish job, core,
версия идентичности, полные доказательства тестов и хеши опубликованных ссылок.
Совместимость старой реализации `8601c067ce2f7dde936b17808b7bf58906131d19` задана
явно; прежний schema 3 без достаточных доказательств не используется. После
миграции `history.json` связан хешем с отчётом; его прежние наблюдения заново
сверяются с независимыми отчётами каждого запуска за 48 часов. Проверяются
связи parent commit и время publish job. Разрешены явно указанные совместимые
commit реализации и точный текущий GITHUB_SHA; новая версия требует явного
решения о совместимости старых измерений. Владельцы с правом записи в репозиторий остаются границей доверия;
эта схема не защищает от намеренной подделки собственным администратором.

История ограничена 48 часами, 32 запусками, 8 192 записями метаданных и 12 МиБ.
Это отдельный лимит: на свежие сетевые проверки по-прежнему максимум 2 048
кандидатов. Все неудачи в пределах окна учитываются без выборочного удаления. Повтор того
же logical run ID не добавляет уверенности: уже опубликованный ID не может
публиковаться ещё раз как новое наблюдение. При несовместимости, некорректной
истории или превышении лимита новый набор не публикуется. Результаты неудач
сохраняются по ID для честного знаменателя; URI никогда не прошедших узлов в
`history.json` не сохраняются. Исходные байты до `#` сохраняются; при миграции
используется точная прежняя опубликованная ссылка, а не выдуманный оригинальный
фрагмент имени. Внутренний старый суффикс метки не удваивается.

В отчёте отдельно указаны текущий upstream-набор, добавленные исторические
кандидаты, общее покрытие и причины распределения по двум спискам. Исторический
список sources у узла не означает, что эти источники содержат его сейчас:
присутствие определяется отдельным `current_ids`.

В Karing можно добавить основной URL и выставить обновление подписки раз в
2 часа, резерв держать отдельно. Это рекомендация: настройки устройства этот
репозиторий не меняет. Ваша сеть может давать другие результаты; доступ из
России/конкретного оператора и воспроизведение HD-видео не подтверждены.

## Проверки качества

1. Два независимых HTTPS 204 endpoint: gstatic и Cloudflare. Достаточно одного
   корректного ответа с проверенным сертификатом, HTTP 204, пустым телом и
   временем до 10 секунд. Отказ второго виден в диагностике: блокировка одного
   вспомогательного сайта не равнозначна неисправности всего прокси
2. Через тот же процесс core и выбранный IP повторяются проверки примерно на
   15-й, 30-й и 45-й секундах. Все три должны пройти. Повторная попытка допускается
   только для фиксированного списка временных сетевых/HTTP-ошибок
3. До и после этого окна полностью загружаются 2 МиБ с Cloudflare. Каждый
   успешный образец должен достигать 256 КиБ/с (около 2 Мбит/с), включая время
   соединения. Медленный/частичный образец можно повторить один раз; оба итоговых
   образца обязательны. Нет обещания HD/4K, длительной работы или неизменности IP
4. Главные страницы YouTube/ChatGPT запрашиваются без cookies, логинов, токенов,
   редиректов и решения CAPTCHA. HTTP 200 плюс признаки подлинной страницы,
   отсутствие видимой защитной/consent-страницы. Временные ошибки можно
   повторить один раз. 403, редирект или challenge сохраняются как наблюдение

Отклонённый узел называется неподтверждённым данным тестом, а не безусловно
«мёртвым». Скорость зависит в том числе от Cloudflare; такой отказ не доказывает
общую непригодность. 45 секунд не измеряют многодневную надёжность или потери
пакетов. Никаких прямых запросов в обход тестируемого прокси при сбое нет.

## Откуда проверяется доступность

Обычные публичные GitHub-hosted `ubuntu-24.04` runners. Это **не подтверждение
доступности из России**, с вашего Android или конкретного домашнего/мобильного
оператора. Местоположение прокси и тестовой машины — разные вещи; российский
выходной IP не подтверждает доступность прокси из России.

`probe_origin` сообщает происхождение измерения и всегда сохраняет
`russia_verified=false`, `country=unknown` в этой реализации. Схема содержит
стабильную identity version, время, core build и source snapshot, чтобы позднее
можно было сопоставлять отдельные авторизованные измерения из реальной сети.
Приём внешних «российских» отчётов пока не реализован: самозаявленная страна
не является доверенным доказательством. Нужен непосредственный измеритель в
конкретной российской сети; даже его успех не доказывает работу у всех операторов.
Не изменяются пользовательские VPN, DNS, firewall или настройки устройства.

## Источники и полное покрытие

Шесть публичных candidate feeds, точные URL находятся в `checker.SOURCES`:
- igareck: `BLACK_SS+All_RUS.txt`, `BLACK_VLESS_RUS_mobile.txt`, `BLACK_VLESS_RUS.txt`
- Diversan313/apex-parser: `subs/main/alive_bl.txt`
- VovaplusEXP/p-configs: `Splitted-By-Protocol-Secure/vless.txt`
- mahdibland/V2RayAggregator: `Eternity.txt`

Они не считаются автоматически проверенными. Каждый источник скачивается в
ограниченном объёме (4 МиБ, 20 000 строк). Отчёт содержит SHA-256 точных полученных
байтов, время получения, количество строк/конфигураций и фиксированные причины
отсева. Хеш связывает результат с содержимым даже при изменении upstream;
это не выдуманный commit SHA источника.

Дедупликация основана на поддерживаемых параметрах успешного аутентифицированного потока, включая
учётные данные, TLS, transport, path и параметры, а не IP/страну/метку.
Варианты, различающиеся только REALITY fallback `spx`, могут объединяться: это
идентичность проверяемого потока, не полная идентичность поведения любого клиента. Разные
полезные варианты на одном адресе не удаляются. ID не меняется при переименовании
источником. Сохранён SHA-256 исходной URI для трассировки.

`prepare` создаёт неизменяемый manifest; каждый shard получает до 64 кандидатов.
Одновременно до 8 обычных runners и 4 проверки в каждом. Никаких платных размеров
runner или изменений биллинга. Все shards привязаны к одному manifest digest,
commit реализации и закреплённому core. Сборка отказывает при дубликатах, пропусках,
другой версии/manifest, несовпадении экспорта или устаревших данных.

Жёсткий защитный максимум — 2 048 поддерживаемых уникальных конфигураций,
60 минут на shard. Превышение не приводит к усечению: новый запуск не публикуется
и сообщает необходимость пересмотра бюджета. `complete_supported=true` означает
полный разобранный набор всех шести источников плюс сохранённые кандидаты, не все неизвестные форматы и
не подтверждение работы у пользователя. Неподдерживаемые варианты учитываются
как неподдерживаемые, а не как сетевые отказы.

Верхняя граница тела запросов на кандидата: 8 МиБ speed (два образца, две попытки)
+ 8 МиБ страниц (два сервиса, две попытки) + небольшие HTTPS204, source downloads,
core archives и протокольные накладные расходы. До 32 ГиБ этих тел на абсолютный
предел 2 048; обычно значительно меньше из-за ранних отказов. Проверяются максимум
3 публичных адреса одного endpoint перед углублённой проверкой; остальные
учитываются в числе DNS-ответов, но не выдаются за проверенные.

В `resources` отчёт фиксирует реально сообщённые curl байты тел, число HTTP
попыток, время до завершения проверок и сумму секунд shards. Это не полный
сетевой трафик: TLS/proxy overhead и неучтённые оборванные тела не включены.
История расширяет нагрузку: ранее замерено примерно 13–23 минуты и 1,6–2,4 ГиБ
тел на 499–781 кандидате; это ориентир, а не обещание длительности нового набора.
Лимиты не ослабляются, для публикации всё равно требуется полный результат.

## Парсер, безопасность и границы совместимости

Строго закреплён sing-box 1.14.2. Официальный архив проверяется по SHA-256 до
извлечения; binary digest записывается отдельно и проверяется в каждом shard.
Перед подключениями выполняется `sing-box check` для всех конфигураций shard.

Поддержаны AEAD Shadowsocks и валидированные SS2022, встроенный `obfs-local`
только `obfs=tls`, VLESS TLS/REALITY, VMess TLS alterId=0, Trojan TLS и Hysteria2 TLS.
Неизвестные опции, нешифрованные варианты и запросы отключить TLS verification
отклоняются. Значения insecure `0`, `false` и пустое означают явно выключенный
флаг, но никогда не включают insecure. Ничего из URI не запускается как команда.

Особые ограничения:
- XHTTP не поддерживается core 1.14.2 и не переименовывается в TCP/WS
- gRPC — только обычный Gun/default без независимого непустого authority;
  HTTPUpgrade — native transport без early-data query
- `xtls-rprx-vision-udp443` остаётся неподдерживаемым
- `packetEncoding=none` преобразуется во внутреннее явное пустое значение;
  исходная URI не меняется. HTTP-тесты не подтверждают UDP-поведение Karing
- REALITY `spx` не влияет на успешный аутентифицированный поток, поэтому
  игнорируется внутри тестового core. Поведение failed-auth camouflage/crawler
  может отличаться; исходный `spx` сохраняется для клиента
- Текущий импортёр Karing недоступен для полного публичного аудита. Исторические
  исходники и upstream-спецификации помогают адаптеру, но не доказывают точную
  эквивалентность любой установленной версии Karing

Все DNS-ответы должны быть public: private, loopback, link-local, multicast,
IPv6 transition и mixed public/private отклоняются. Core подключается к
зафиксированному IP, а экспорт сохраняет исходное имя. DNS клиента может выбрать
иной IP позднее; это явная граница проверки. SOCKS слушает только loopback с
одноразовым случайным паролем. HTML, stderr core/curl, cookies и пароли не
попадают в публичный отчёт; в нём только фиксированные категории, endpoint
проверки, публичный адрес прокси, UTC и числовые измерения.

## Свежесть, публикация и запуск

Расписание — примерно каждые 2 часа (`23 */2 * * *` UTC); GitHub может задерживать
cron. Новый набор публикуется только целиком после независимой проверки.
Самое старое измерение должно быть младше двух часов при публикации; готовый
report — младше часа. Если подходящих узлов нет при полном корректном запуске,
список пуст. Старые успешные узлы не получают новый verified-статус автоматически.

При неудачном/незавершённом запуске предыдущая публикация остаётся по прежнему
URL **со старой датой**. Считайте её устаревшей спустя 12 часов. Это явный last-good
snapshot, не новая проверка; raw URI-list и Karing не обязаны автоматически
соблюдать это ограничение. Сохранённая история `checked` позволяет разбирать
изменения. Предыдущие узлы можно повторно проверять только как кандидатов,
не переносить результаты в новый успешный запуск.

Actions → Check public subscription → Run workflow по умолчанию выполняет
проверку **без публикации**. Для обновления `checked` нужен `publish=true` и
ветка `main`; schedule публикует автоматически. Write-token есть только у
заключительного publish job. Результаты экспериментальных веток URL не заменяют.

Offline tests не подключаются к прокси:

    python3 -m unittest discover -s tests -v
    python3 -m py_compile checker.py uri_parser.py production.py validate_output.py fetch_core.py

Реальное тестирование выполняйте на отдельной машине без приватных сервисов.
Команды `production.py --help` описывают prepare/check/merge/verify-public.
`checker.py` оставлен как однопроцессный локальный convenience entry point;
для полного production-покрытия используется workflow с shards.
